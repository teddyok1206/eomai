# Codex usage refresh while execution capability is limited

Usage exhaustion and model compatibility are different observations. An operator may need to refresh the former while the latter remains `DEGRADED`; neither observation grants worker execution.

The 2026-10-28 read-only operating check found all six bindings `DEGRADED` with `CAPABILITY_OBSERVATION_FAILED`: the protected worker executable SHA differs from the reviewed policy's runtime pin. This is not evidence that all six quotas are exhausted. A provider reset alone cannot restore execution; a fresh official compatibility report and policy installation are separate requirements.

- **Owner and source:** the existing Orchestrator `OBSERVE` command owns the fixed-slot probe. Its canonical inputs are the exact binding/version, the local login-status probe, and the sanitized Codex App Server usage response. API and Web only project the committed command result. No worker-to-worker or direct database access is added.
- **Identity and pointers:** keep the command ID, binding ID, assignment and resource version, usage observation hash, result hash and immutable command history distinct. Reuse the existing fixed-slot handoff and read validation. The newer result schema `codex-control-command-result/1.3` applies only when login-status was `READY` but capability verification became `DEGRADED`; released 1.0–1.2 bytes and meanings stay fixed.
- **Access and scale:** one indexed binding lookup and one bounded fixed-slot probe per operator command; the API's binding-scoped latest-observation query includes 1.3. At most six fixed accounts are displayed. No new index, queue, table or binary payload is needed.
- **Concurrency:** an active/reconciling lease or login-change enrollment still prevents a separate App Server probe. During either condition the UI button refreshes only the read-only account projection; once idle, it submits the normal `OBSERVE`. Account usage at 100% does not block either path.
- **Failure/retry:** authentication failure does not authorize a usage probe. A usage probe failure remains a failed command; no previous observation is rewritten. A degraded capability result may carry fresh usage but is never treated as a supported model or execution admission. The existing idempotency key and command lease remain authoritative.
- **Simpler alternative:** relabeling a degraded binding as `READY` to fit the old result schema would falsely enable execution. Dropping the usage observation would leave the refresh button ineffective. A narrow successor result keeps both facts honest.
